# MariaDB backup / restore runbook

> Scope: TestApp MariaDB 12.3 persistence. This document defines the repository-controlled logical backup baseline and restore verification procedure. Provider-native snapshots/PITR remain a deployment responsibility.

## 1. Recovery objectives

Initial engineering targets for the self-hosted/Compose baseline:

- **RPO:** <= 24 hours — at least one successful logical backup per 24h.
- **RTO:** <= 4 hours — restore a verified backup and return the API to service within four hours.

These are baseline engineering targets, not a contractual SLA. If production business criticality requires an RPO below 24 hours, enable database-provider/native snapshots and point-in-time recovery (binlog/PITR) in addition to the portable logical backup described here.

## 2. Backup layers

Production should use two complementary layers:

1. **Primary recovery layer:** infrastructure/provider-native snapshot/PITR appropriate for the deployed MariaDB platform.
2. **Portable recovery layer:** compressed `mariadb-dump` generated by `scripts/mariadb-backup.sh`.

The logical dump includes schema, data, triggers, routines and events, is created with a single transaction, is gzip-compressed and receives a SHA-256 sidecar checksum.

Do not treat a successful backup command as proof that recovery works. A backup is operationally valid only after periodic restore verification.

## 3. Create a logical backup

Required environment:

```text
MARIADB_PASSWORD      database password (required)
MARIADB_HOST          default 127.0.0.1
MARIADB_PORT          default 3306
MARIADB_DATABASE      default testapp
MARIADB_USER          default root
MARIADB_IMAGE         default mariadb:12.3
BACKUP_DIR            default backups
```

Example for the local Compose database:

```bash
MARIADB_PASSWORD=root \
  bash scripts/mariadb-backup.sh backups/testapp.sql.gz
```

Outputs:

```text
backups/testapp.sql.gz
backups/testapp.sql.gz.sha256
```

Store the dump and checksum outside the database host/volume. Production credentials must come from the deployment secret store and must not be committed to the repository.

## 4. Verify a restore safely

`scripts/mariadb-restore-verify.sh` never restores over the source database. It creates a disposable target database, restores the dump there, verifies it and drops the target on exit.

Required environment:

```text
MARIADB_ADMIN_PASSWORD   admin password (required)
MARIADB_ADMIN_USER       default root
MARIADB_SOURCE_DATABASE  default testapp
MARIADB_HOST             default 127.0.0.1
MARIADB_PORT             default 3306
MARIADB_IMAGE            default mariadb:12.3
```

Example:

```bash
MARIADB_ADMIN_PASSWORD=root \
  bash scripts/mariadb-restore-verify.sh \
  backups/testapp.sql.gz \
  testapp_restore_verify
```

The verifier checks:

- backup SHA-256 when the sidecar exists;
- gzip integrity;
- successful restore into an isolated database;
- source and restored base-table counts are equal;
- `__EFMigrationsHistory` row counts are equal and non-zero;
- optional caller-supplied verification query/value.

For a data marker check:

```bash
VERIFY_QUERY="SELECT COUNT(*) FROM idempotency_records WHERE Operation='restore.probe';" \
VERIFY_EXPECTED=1 \
MARIADB_ADMIN_PASSWORD=root \
  bash scripts/mariadb-restore-verify.sh backups/testapp.sql.gz testapp_restore_verify
```

## 5. CI recovery drill

The main GitHub Actions pipeline performs the following after applying migrations from the production image:

1. writes a deterministic marker into the real application table `idempotency_records`;
2. creates a logical backup of the migrated `testapp` database;
3. restores it into `testapp_restore_verify`;
4. verifies table count, migration history and marker preservation;
5. removes the disposable restore database.

This catches incompatible dump/restore tooling and schema changes on every `beta-ddd` pipeline.

## 6. Production restore procedure

During an incident:

1. stop or drain API/worker writes;
2. identify the newest backup/PITR point satisfying the incident boundary;
3. validate backup checksum before destructive actions;
4. restore into a **new database/schema first** where possible;
5. run schema/migration-history and business smoke checks;
6. repoint the application only after verification;
7. check `/health/ready`, login, author read, assignment read and one controlled write path;
8. resume workers/API traffic;
9. preserve the failed database until incident analysis is complete;
10. record actual RPO/RTO and any data loss in the incident report.

Do not run application migrations against an unverified restored database merely to make it start. First establish whether the chosen backup corresponds to a schema version supported by the deployed API image.

## 7. Retention baseline

Until a deployment-specific compliance policy is approved:

- keep daily logical backups for at least 7 days;
- keep at least one weekly portable backup for 4 weeks;
- keep backup metadata/checksums with the backup object;
- encrypt production backups at rest and in transit using the storage/platform facilities;
- ensure backup storage credentials are separate from normal application DB credentials.

Longer retention and legal/compliance retention must be set by the deployment owner, not hard-coded in application runtime.

## 8. Remaining D1 deployment gate

Repository automation proves logical recoverability in CI. Before production 1.0, perform and record at least one restore drill in the actual staging/production-like database platform, including measured restore duration and a readiness/business smoke test. That external drill is intentionally not marked complete merely because CI restore verification is green.
